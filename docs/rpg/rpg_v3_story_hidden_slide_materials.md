# RPG v3 Story-Hidden-Cause Slide Materials

## Slide 1: Research Goal

### Concise slide bullets

- Move from answer lookup to scientific discovery.
- The agent must infer a hidden cause that is implied by the story but not listed as a variable.
- The key behavior is hypothesis formation, targeted experimentation, and mechanism-based explanation.
- We want problems where the next experiment is chosen because of a theory, not because the agent is enumerating arms.

### Details / if asked

The new RPG direction is meant to test whether an LLM can act like a scientist in a partially observed world. The hidden cause is not named as `LatentVariable` or exposed as an observed column. Instead, the world story contains ordinary objects, processes, and constraints that could plausibly create the observed pattern. The model has to notice those semantic clues, propose a hidden mechanism, and query data that would distinguish that mechanism from alternatives.

The important difference from the earlier static RPG tasks is that the answer should not collapse to "try every named intervention and pick the best mean." A good trajectory should include: initial observations, a candidate latent explanation, an experiment that specifically tests the mechanism, at least one alternative explanation ruled out, and a final answer that explains why the action follows from the mechanism.

## Slide 2: Example Scientific Pattern

### Concise slide bullets

- Surface clue: a visible variable predicts the outcome.
- Hidden cause: the visible variable is only a clue to an unobserved state.
- Mechanism proxies: separate measurements reveal how the hidden state affects the outcome.
- Decisive experiment: intervene on the hypothesized mechanism and check whether the proxies and outcome move together.

### Details / if asked

In the gutter-style example, leaf fall is not the causal answer. Leaf fall is a clue. The hidden cause is obstruction in the roof-drainage path. If this hypothesis is right, we should see delayed downspout discharge, roof-edge overflow, and flooding move together. Clearing the gutter or running a controlled flow test should reduce the mechanism proxies and the downstream flooding.

This is the kind of reasoning we want in other domains too. For example, in a clinic world, a symptom flare might be a clue to an unobserved medication interaction or hidden infection. In a factory world, a visible defect pattern might be a clue to a hidden calibration drift. In a school world, a drop in performance might be a clue to an unobserved prerequisite gap. The concrete story changes, but the scientific pattern is the same.

## Slide 3: What The Scientist Sees

### Concise slide bullets

- Story in natural language.
- Observed continuous measurements.
- Public actions the scientist may try.
- Query budget and allowed query modes.
- No hidden variables, oracle scores, role labels, or gold answer.

### Details / if asked

The scientist sees the public `visible` block only. It sees the story, measurement catalog, action catalog, question, budget, and answer schema. It does not see the hidden simulator config, continuous equations, role map, validator checks, oracle action scores, or gold answer.

This matters because the benchmark should reward discovery from data and semantics. Role labels such as `visible_trigger`, `mechanism_proxy_primary`, and `targeted_fix_primary` exist only inside the generator/simulator so that different LLM-created worlds can share a valid causal shape without leaking the solution to the agent.

## Slide 4: New World Generation Design

### Concise slide bullets

- One archetype: `story_hidden_cause_discovery`.
- Concrete worlds are generated by an LLM template prompt.
- The LLM creates the story, hidden cause, measurements, actions, scoring terms, and gold explanation.
- The simulator instantiates continuous relations from role labels.
- This avoids hardcoding a single gutter question.

### Details / if asked

The archetype is fixed, but the concrete world is not. The LLM template prompt asks for a fresh domain and a structured JSON blueprint. The blueprint includes the hidden cause in ordinary language, accepted aliases, a story where the hidden object/process/state is casually present, observed variables, public actions, semantic scoring terms, and a gold explanation.

The simulator then uses required roles to generate samples. For example, the role `visible_trigger` might be leaf fall in a home world, shift humidity in a factory world, or refill timing in a clinic world. The hidden continuous state is generated from the trigger, exposure, and maintenance-like variables. That hidden state drives mechanism proxies and the outcome. Targeted actions reduce the hidden state; alternative actions affect plausible decoys.

## Slide 5: Why Continuous Relations Matter

### Concise slide bullets

- Variables are continuous 0-100 measurements, not categorical BN nodes.
- Relations are generated by functions with noise.
- Hidden causes influence mechanism proxies and outcomes continuously.
- Gold answers come from Monte Carlo intervention scoring plus semantic/trajectory checks.

### Details / if asked

This version moves away from a categorical Bayesian-network framing. The public data are continuous measurements. The hidden state is also continuous, such as an obstruction level, calibration drift severity, or unobserved burden. Observed correlations emerge from noisy functions rather than from discrete categories.

The oracle does not simply look up a category. It samples many units, applies interventions, computes expected utility, and stores action scores. For the latent-cause answer, scoring also checks whether the submitted explanation semantically matches the hidden cause, includes multiple evidence families, rules out alternatives, proposes or performs a decisive test, and recommends a targeted action.

## Slide 6: Action Space

### Concise slide bullets

- Current v3 worlds expose 10 binary public actions.
- Each interventional query may set up to 3 actions jointly.
- Nominal joint-action space: `1 + C(10,1) + C(10,2) + C(10,3) = 176`.
- This is larger than the old handpicked action list.
- But action-space size alone is not enough; the agent must explain the hidden mechanism.

### Details / if asked

The current generator gives the scientist 10 binary actions. A query can set any subset of up to 3 actions, so the possible joint interventions include no action, all single actions, all pairs, and all triples. That gives 176 candidate intervention conditions.

This is a real improvement over the old gutter pilot, where the stored oracle only scored 16 handpicked interventions. However, brute-force enumeration is still not the desired scientific behavior. The benchmark should reward an agent for choosing an experiment because it has a mechanism hypothesis. That is why the scoring now requires both semantic explanation and a trajectory check showing that the agent actually queried a mechanism-targeted intervention with relevant mechanism/outcome measurements.

## Slide 8: What A Good Trajectory Looks Like

### Concise slide bullets

- Observe the outcome, trigger, context, and candidate mechanism proxies.
- Form a hidden-cause hypothesis in ordinary language.
- Query a targeted intervention that should affect the mechanism.
- Compare against plausible alternatives.
- Answer with cause, evidence, alternative ruled out, decisive test, and action plan.

### Details / if asked

A good scientist should not immediately submit an answer from the story. It should collect enough data to see whether the story-implied hypothesis explains the pattern. It should also avoid treating the visible trigger as the final cause. For example, "leaf fall causes flooding" is not sufficient; the better answer is "leaf fall is evidence for a hidden gutter obstruction that redirects roof runoff."

The current scorer enforces this qualitatively and procedurally. A latent-cause answer must match the hidden mechanism semantically, include several families of evidence, rule out at least one alternative, include a verification test, and recommend a targeted action. The world model also checks the trajectory: the agent must have run an interventional query involving a targeted/diagnostic action and measured mechanism/outcome variables.

## Slide 9: What We Are Testing

### Concise slide bullets

- Can the agent invent a hidden variable from story context?
- Can it decide which measurements are mechanism proxies?
- Can it choose experiments that distinguish hypotheses?
- Can it avoid surface-correlation explanations?
- Can it explain why an action follows from the mechanism?

### Details / if asked

This benchmark is about latent discovery in a broad sense. The agent is not asked to estimate a named latent variable. It must hypothesize that such a variable exists. That is closer to real scientific reasoning: researchers often infer unobserved mechanisms from patterns, proxies, and interventions.

The ideal failure mode is not a formatting error or a black-box arm-ranking mistake. The interesting failures are scientific: the agent mistakes a clue for a cause, tests the wrong mechanism, fails to rule out a plausible alternative, or recommends an action that improves the outcome but does not match its explanation.

## Slide 10: Why This Is Not A Black Box Task

### Concise slide bullets

- The final answer is explanatory, not just predictive.
- The agent must name the hidden cause in ordinary language.
- The trajectory must include mechanism-targeted verification.
- The same best action without the right explanation is not the full success condition.

### Details / if asked

A pure black-box version would let the agent sample every action and choose the best outcome. That is not the goal. Here, the action recommendation is only one part of the answer. The scientist must say what hidden state caused the pattern and why the chosen action targets it.

This is why the prompt explicitly tells the agent that visible predictors may be clues rather than causes. It encourages inventing hypotheses for unobserved objects, processes, failure modes, diagnoses, or environmental states based on the story. The world model then requires a mechanism-verifying query before accepting a latent-cause answer.

## Slide 11: Pipeline Files

### Concise slide bullets

- `world_gen_rpg.py`: generates LLM-template story-hidden worlds.
- `simulator_rpg.py`: executes samples and scores answers.
- `world_model_rpg.py`: exposes the query interface and enforces trajectory checks.
- `scientist_agent_rpg.py`: prompts the scientist agent.
- `run_agent_batch_rpg.py`: runs batches.
- `evaluate_rpg.py`: evaluates completed runs.

### Details / if asked

The generation side and pipeline side are now separated. `world_gen_rpg.py` creates world JSONs with hidden simulator config and public visible fields. The runtime pipeline loads those worlds, strips hidden fields from the scientist, executes strict JSON queries, logs every turn, and scores the final answer.

The important v3 compatibility change is that scoring and trajectory checks are template-aware. They no longer assume that the mechanism must literally be called gutter/downspout. The generator stores scoring terms and trajectory requirements for each LLM-created template, and the evaluator uses those fields.

## Slide 15: What To Look For In The New Run

### Concise slide bullets

- Are the generated domains diverse?
- Does the story imply the hidden cause without revealing it?
- Does the agent invent the right hidden variable?
- Does it query mechanism proxies before answering?
- Does it test targeted actions rather than enumerate everything?
- Do failures look scientifically interesting?

### Details / if asked

For each generated world, first inspect `rpg_story_hidden_templates.json`. Check whether the story is coherent and whether the hidden cause is casually present but not explicitly identified as the answer. Then inspect the generated world JSON to confirm the public names do not leak the hidden cause too directly.

For each agent trace, look for whether the model forms multiple possible explanations and chooses experiments to distinguish them. A high-quality success should not just say "Action X improved outcome." It should explain why Action X tests the hypothesized mechanism and why alternatives are less plausible.

## Slide 16: Current Risks

### Concise slide bullets

- LLM-generated worlds may still be too semantically obvious.
- Action names can accidentally leak the answer.
- The agent may succeed by testing a small number of obvious actions.
- The scorer is semantic, so aliases and term coverage matter.
- Need qualitative audit before trusting accuracy.

### Details / if asked

The biggest risk is that the LLM creates stories where the hidden cause is too easy. If the hidden object is repeatedly mentioned and the targeted action name directly names it, then the agent can solve the task mostly from common sense. We should reject or revise templates where the answer is visible from names alone.

Another risk is that the simulator role structure is shared across worlds. That is acceptable for early v3 because it gives us controlled validity, but later versions should add more mechanism families so agents cannot learn one generic pattern.

## Slide 17: Why This Is A Better Direction

### Concise slide bullets

- It aligns with the PI's latent-discovery framing.
- It creates larger, combinatorial action spaces.
- It requires semantic hypothesis generation.
- It keeps continuous simulator relations and faithfulness-style checks.
- It gives useful qualitative traces for scientific reasoning.

### Details / if asked

The earlier benchmark mostly tested whether a model can run a few controlled comparisons. This redesign asks whether the model can decide what unobserved state would make the observed world coherent. That is closer to how scientists reason from partial evidence.

The action space is now larger, but the central difficulty is not merely combinatorial search. The important challenge is deciding which part of the action space is scientifically meaningful given a hypothesized mechanism. This lets us evaluate not only final accuracy, but also the process: what hypotheses the agent considers, what experiments it chooses, and how it interprets the results.
